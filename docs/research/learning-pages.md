# Make every card teach its own code

No team has published a proven "learning page per ticket" practice yet. The evidence still points clearly at one: a **one-screen page per Jira card**, drafted by a cheap subagent from the PR diff, with one diagram and one **explain-back question the developer answers in their own words**. The risk is real. Two independent randomized trials found that unguided AI help leaves people about **17% worse when they later work without it** (50% vs 67% on a coding quiz, d = 0.74), and they get almost no speed gain for it ([Anthropic](https://www.anthropic.com/research/AI-assistance-coding-skills); [PNAS](https://www.pnas.org/doi/10.1073/pnas.2422633122)). People don't notice the loss. Experienced developers measured 19% slower with AI believed they were 20% faster ([METR](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)). The harm comes from delegation, not from AI itself. Developers who asked for explanations or studied the generated code scored at or above the no-AI group. Two cheap techniques add the most per minute of reading: self-explanation (g = 0.55) and a retrieval question with feedback (g = 0.73) ([Bisra 2018](https://gwern.net/doc/psychology/spaced-repetition/2018-bisra.pdf); [Rowland 2014](https://courseware.epfl.ch/assets/courseware/v1/fdde2f0aa590bf3b1324077a6bf1540c/asset-v1:EPFL+DEMO+2020+type@asset+block/Rowland2014-meta-analysis.pdf)). Long formats get abandoned. Half of the repos that adopt ADRs stop before writing five ([arXiv 2604.03826](https://arxiv.org/html/2604.03826)). So keep the page short, tie it to a step the team can't skip (the PR), and keep it cheap by feeding the agent the diff, not the whole repository.

## The recommendation for a 3-5 person team on Claude Code, Jira and Notion

This is a synthesis. No source prescribes this exact page. Each piece borrows from a format that has evidence or a long track record behind it, and the source for each piece is shown below.

**Page sections, in order, about 250-400 words (3-5 minutes to read):**

| # | Section | Size | Borrowed from |
|---|---|---|---|
| 1 | Title "About `<feature>`" + links to the card and PR | 1 line | Diátaxis explanation |
| 2 | TL;DR: what the user can now do, and the one idea behind it | 2-3 lines | design-doc context |
| 3 | Why, and what this card deliberately does *not* do | 2-4 lines | Google goals and non-goals |
| 4 | Flow diagram: one Mermaid sequence or flowchart covering the main path only | 1 diagram, at most about 8 participants | C4 dynamic diagram |
| 5 | Where it lives: files that matter, one line each | at most 6 rows | CodeRabbit changed-files table |
| 6 | Key decision and the alternative rejected | 2-3 lines | ADR consequences, design-doc alternatives |
| 7 | Gotchas: what would break it, what surprised the agent or reviewer | 2-4 bullets | arc42 risks |
| 8 | How to check it works (one command or one click path) | 1-3 lines | docs-as-code |
| 9 | Explain-back: 1-2 questions, with a model answer in a collapsed toggle | 2 questions | self-explanation and retrieval research |

Add a glossary line only when the card introduces a new domain term. Leave out component and code-level diagrams because they go stale fastest ([datadef.io](https://datadef.io/guides/en/c4-model-in-practice)). Link to one shared system context and container diagram instead ([c4model.com](https://c4model.com/diagrams)).

**When it's written and updated.** The draft is written when the PR opens. It's patched only when a review-fix commit touches something a section describes. It's finalised in the same PR as the code, and closing the card requires it. When a later card changes the same feature, that card patches the existing page and adds its own link. It doesn't start a new page. This "same PR, definition of done" rule is the strongest practice for keeping docs from going stale ([Graphite](https://graphite.com/guides/documenting-code-for-better-reviews-best-practices); [Darlo](https://darlotechnicalwriting.com/blog/darlotechnicalwriting-best-practices-for-clear-and-effective-documentation)). Docs that something forces you to touch survive. Docs nothing forces you to touch rot.

**Who writes it, and from which inputs.** One subagent runs on **Sonnet**, and **Haiku** is enough for patch-only updates. Anthropic's own cost guidance recommends Sonnet for most work, Haiku for simple subagent tasks, and subagents for verbose work so only a summary comes back ([Claude Code costs](https://code.claude.com/docs/en/costs)). The inputs are the `git diff` against the base branch, the card text and acceptance criteria, the PR description, and a short summary of the agent session. The page template, writing rules and the shared system diagram go first in the prompt so they get cached. Cache reads cost 0.05-0.1x the normal input price ([Anthropic prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)). Skip diffs below a size threshold, the way the Claude Code autodoc action does ([solmaz.io](https://solmaz.io/log/2025/05/24/claude-code-pr-autodoc-action/)). Don't send the whole repository. Red Hat's diff-scoped pipeline with cached folder summaries cut runtime from about 20 minutes to about 4 ([Red Hat Developer](https://developers.redhat.com/articles/2026/04/21/ai-powered-documentation-updates-code-diff-docs-pr-one-comment)). A human approves the page in the PR before it's posted to Notion.

**When to generate an illustration.** Use Mermaid by default. It costs only its own text tokens, renders natively in Notion and GitHub, and the agent can patch it instead of redrawing it ([GitHub](https://github.blog/developer-skills/github/include-diagrams-markdown-files-mermaid/); [Luke Merrett](https://lukemerrett.com/using-mermaid-flowchart-syntax-in-notion/)). Generate an image only when the card introduces a **new domain concept or one key design idea** that a sequence diagram can't show. Typical cases are the first card in a new area, or an idea like "all state lives in one place". The image should show one concrete scenario and leave everything else out ([Julia Evans](https://jvns.ca/blog/2018/10/28/when-does-teaching-with-comics-work-well/)). Expect about one card in five or fewer to need one. At roughly $0.01-0.04 per medium-quality image, cost doesn't drive this decision, but review time does ([pricepertoken.com](https://pricepertoken.com/gpt-image-pricing), secondary).

**How the team uses the explain-back question.** The developer who shipped the card writes the answer **in their own words before merge**, then opens the model answer. The reviewer reads that answer as part of the review. A wrong or vague answer means the code isn't understood yet, the same way a red test means it isn't working yet. At the weekly sync, each person answers one question from a teammate's page *without looking*, so the retrieval happens days later. That gap is where testing beats rereading: 56% vs 42% recall at one week, while rereading still wins at five minutes ([Roediger and Karpicke 2006](https://colinallen.dnsalias.org/Readings/2006_Roediger_Karpicke_PsychSci.pdf)). Write questions most people can answer from the page. Retrieval practice stops working when fewer than half of attempts succeed (g = 0.03) ([Rowland 2014](https://courseware.epfl.ch/assets/courseware/v1/fdde2f0aa590bf3b1324077a6bf1540c/asset-v1:EPFL+DEMO+2020+type@asset+block/Rowland2014-meta-analysis.pdf)). Good questions are "why", "what breaks if" and "trace this request" questions, not trivia.

## Delegation, not AI, is what erodes understanding

The Anthropic trial had 52 mostly junior engineers learn an unfamiliar Python library. The AI group finished about two minutes faster, a difference that wasn't significant, and scored **17 points lower** on a later quiz without AI. The biggest gap was on debugging ([Anthropic](https://www.anthropic.com/research/AI-assistance-coding-skills)). Bastani's trial of about 1,000 maths students found the same 17% drop, and found that an AI limited to giving hints removed it ([PNAS](https://www.pnas.org/doi/10.1073/pnas.2422633122)). How people used the AI mattered more than whether they used it. Delegators scored 24-39%, while people who asked conceptual questions or mixed code with explanations scored 65-68%. These subgroups are small and exploratory. Kazemitabaar's study added a step where learners modified the code after each AI-generated task, and found **no retention loss at one week** ([arXiv](https://arxiv.org/pdf/2302.07427)). The common thread is that an active comprehension step cancels the harm. Note one limit. A hint-only guardrail prevented the loss but didn't improve learning, so a team still needs an active step, not just a careful prompting style.

People don't feel this loss. METR's experienced developers misjudged their own speed by about 40 percentage points ([METR](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)). Microsoft and CMU found that more trust in AI goes with **less critical thinking** ([Microsoft Research](https://www.microsoft.com/en-us/research/wp-content/uploads/2025/01/lee_2025_ai_critical_thinking_survey.pdf)). That's why the recommendation measures understanding with an explain-back instead of asking "did you get it?". Osmani calls the gap *comprehension debt*: green tests and clean code sitting on top of a mental model that's eroding ([O'Reilly Radar](https://oreillyradar.substack.com/p/comprehension-debt-the-hidden-cost)). Storey splits it into cognitive debt, which lives in people, and intent debt, which is the missing goals and rationale in artifacts ([ACM Queue](https://queue.acm.org/detail.cfm?id=3807966)). The "why" and "rejected alternative" sections of the page target intent debt directly. Thoughtworks Radar Vol. 34 tells teams to adopt explicit countermeasures ([Thoughtworks](https://www.thoughtworks.com/content/dam/thoughtworks/documents/radar/2026/04/tr_technology_radar_vol_34_en.pdf)).

There are honest limits here. Every skill-loss trial studied people learning something new over minutes or a semester. **No study measures professionals in their own codebase over months**, and none studies agentic tools such as Claude Code. Nobody has a validated metric for comprehension debt yet. The available proxies are PR size, churn, AI-authored share, and direct checks such as an explain-back.

## Learning science gives the page its active parts

Three findings set the page's shape. Prompted self-explanation has a meta-analytic effect of **g = 0.55** across 5,917 participants. It rises to 0.67 against no explanation, and falls to only 0.35 against simply being handed an explanation ([Bisra 2018](https://gwern.net/doc/psychology/spaced-repetition/2018-bisra.pdf)). So the developer's own answer is worth more than a better-written page. Retrieval practice averages **g = 0.50, and 0.73 with feedback** ([Rowland 2014](https://courseware.epfl.ch/assets/courseware/v1/fdde2f0aa590bf3b1324077a6bf1540c/asset-v1:EPFL+DEMO+2020+type@asset+block/Rowland2014-meta-analysis.pdf)). The collapsed model answer is that feedback. Words plus a picture beat words alone on transfer tests, with a median **d of about 1.39**, and the effect is strongest for readers new to the material ([Mayer](https://eddl.tru.ca/wp-content/uploads/2020/01/mayer-multimedia-instruction.pdf)). Those are mostly lab studies from one group, so treat 1.39 as an upper bound.

Length matters less than the active step. Microlearning meta-analyses are small and partly unvetted, but they point at **5-10 minute** units ([ResearchGate](https://www.researchgate.net/publication/394265408_Microlearning_Effectiveness_in_Higher_Education_A_Systematic_Review_and_Meta-Analysis_of_Student_Retention_and_Learning_Outcomes)). In Roediger and Karpicke, one short recall test after a short passage produced the one-week advantage. Nobody has tested 2-minute against 10-minute developer notes head to head. A 3-5 minute read plus one question is the defensible middle.

## What leading teams produce today, and what survives

Teams produce five kinds of artifact. Two of them are written once per change and **survive because something forces them**. The first is the PR summary. In a quasi-experiment, early Copilot-for-PRs users needed **19.3 fewer review hours** and were 1.57 times more likely to merge ([Xiao et al. FSE 2024](https://arxiv.org/pdf/2402.08967)). CodeRabbit posts a walkthrough on every PR with a summary by change type, a one-line-per-file table and Mermaid sequence diagrams ([CodeRabbit](https://docs.coderabbit.ai/pr-reviews/summaries)). The second is the agent instruction file. Boris Cherny's team edits one shared CLAUDE.md several times a week. Reviewers tag `@claude` to add a rule in the same PR, and one engineer keeps a notes directory per task, updated after every PR, that CLAUDE.md points at ([Cherny](https://www.threads.com/@boris_cherny/post/DUMZuyJkpSJ)). Thoughtworks moved curated shared instructions to Adopt ([Thoughtworks](https://www.thoughtworks.com/en-us/radar/techniques/curated-shared-instructions-for-software-teams)).

Artifacts with nothing forcing them **rot**. About half of the repos that use ADRs have fewer than five records, and under 2% keep more than 25 ([arXiv 2604.03826](https://arxiv.org/html/2604.03826)). Spec-driven tools pile up review overhead. Kiro turned a small bug into 16 acceptance criteria ([Böckeler](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)). Thoughtworks also warns that stale ADRs and specs mislead coding agents ([Thoughtworks](https://www.thoughtworks.com/radar/techniques)). Whole-repo wikis such as DeepWiki and Google Code Wiki regenerate after every change, so they can't fall out of date. They can still be confidently wrong, there's no independent accuracy data for them, and they **don't record why** a decision was made ([Devin Docs](https://docs.devin.ai/work-with-devin/deepwiki); [Google](https://developers.googleblog.com/introducing-code-wiki-accelerating-your-code-understanding/)). Session-provenance tools such as Entire Checkpoints and Git AI keep the raw agent trail with each commit ([entireio/cli](https://github.com/entireio/cli); [git-ai](https://github.com/git-ai-project/git-ai)). They're useful for digging into history later, but nobody has shown that people read them. Simon Willison's agent-written "linear walkthroughs" and interactive explainers come closest to the human-facing per-change page ([Willison](https://simonwillison.net/guides/agentic-engineering-patterns/)).

The gap matters. Jira-to-wiki linking exists through Rovo MCP and Smart Links, but I found **no published practice of one learning page per Jira card**, in Confluence or in Notion ([Atlassian Rovo MCP](https://developer.atlassian.com/cloud/rovo-mcp/)). Links help people find the page. They don't keep it current ([Atlassian](https://www.atlassian.com/blog/developers/link-jira-issues-to-confluence-pages-automatically)).

## Keeping it cheap means diff in, patch out

Claude Code averages about **$13 per developer per active day** ([Claude Code costs](https://code.claude.com/docs/en/costs)). One diff-scoped subagent run per card is a small part of that. Nobody publishes a per-document cost figure, so measure your own over the first few weeks. The savings come from five places. The cached prefix holds the template, the rules and the system diagram. The diff is passed as a file instead of exploring the repo. The subagent patches only the sections the diff touches instead of rewriting the page. Small diffs are skipped. Images are made only by exception. Avoid agent teams for this job, because they use about 7x the tokens. The page also pays off a second time: a maintained system overview doubles as agent context, and Anthropic recommends exactly that to cut file reading on later tasks ([Claude Code costs](https://code.claude.com/docs/en/costs)).

## Conclusion

The idea that changes the most is that a better page isn't what matters. The developer's answer to a question about the page matters more. Self-explanation beats being given an explanation by about half a standard deviation, and people can't sense their own comprehension loss. So the explain-back is the core of the practice, and the page is the cheap scaffolding around it. Treat it as a review gate, like a test, and it will last. Treat it as documentation and it will go the way of ADRs.

What's still unknown is whether any of this holds for professionals over months in their own codebase with agentic tools. No study covers that case. A small team can find out cheaply. Track the explain-back hit rate at merge and at the weekly sync for a quarter. If answers stay right a week later, the practice is working. If they don't, make cards and PRs smaller. In Osmani's words, "the unit of review is the unit of comprehension" ([explainx summary](https://explainx.ai/blog/addy-osmani-cognitive-surrender-claude-code-engineer-essay-agents-critical-thinking-checklist-2026), secondary).
