# Why grasp works the way it does

Research done in November 2026. Each design choice below links to the notes behind it.

| Finding | What grasp does about it | Notes |
| ------- | ------------------------ | ----- |
| Handing the thinking to the AI is what loses understanding. In Anthropic's January 2026 trial, developers who delegated scored 17% lower on a quiz with no real speed gain; those who asked conceptual questions or asked for code plus explanation kept their understanding. | Step 2 makes the developer state the why and pick the approach. Questions the user asks are logged on the page. | [learning-pages.md](learning-pages.md), [comprehension-before-and-app-map.md](comprehension-before-and-app-map.md) |
| Missing intent turns into cognitive debt ("intent debt"). Spec-first tools write intent down before code, but long specs for small tasks go unread. | The before half is a short spec that scales with the work: a page targets 300 visible words, never over 400, with the rest folded, and the build is compared against it. | [comprehension-before-and-app-map.md](comprehension-before-and-app-map.md) |
| Answering a question beats rereading (retrieval practice); guessing before learning helps memory for what was guessed (pretesting). | One prediction question before the build, folded away and never blocking. After the build, `walk` is a guided session the owner starts: 5 to 7 questions after real code lines, answers and gaps written to the page, never scored and never blocking. | [learning-pages.md](learning-pages.md) |
| A diagram plus a few words beats words alone. | Mermaid first on every page; one generated illustration per map and issue page when `.grasp.md` says `illustrations: yes`. | [learning-pages.md](learning-pages.md) |
| Docs survive only when a step the team always takes updates them. Hosted auto wikis drift (one measured 29-33 commits behind). | Pages are written inside the run that builds the change, from its diff. | [learning-pages.md](learning-pages.md), [comprehension-before-and-app-map.md](comprehension-before-and-app-map.md) |
| ARCHITECTURE.md-style maps (codemap, invariants, boundaries, names not links) age well. Long generated context files loaded into every session lowered agent success and added about 20% cost. | One app map page, patched per issue, kept in the notebook and out of CLAUDE.md / AGENTS.md. | [comprehension-before-and-app-map.md](comprehension-before-and-app-map.md) |
| Incremental patching costs a small fraction of regeneration and keeps more detail. | Diff in, patch out; one subagent per page, Sonnet to write, Haiku to patch. | [comprehension-before-and-app-map.md](comprehension-before-and-app-map.md) |
| Superpowers-style gates (one question at a time, 2-3 approaches, approval before code, evidence before "done") keep agents honest. | Same gates, in steps 2, 4 and 5. | [packaging-and-workflow.md](packaging-and-workflow.md) |
| Skills load cheaply when SKILL.md is short and detail sits in one-level references; the open Agent Skills format works across Claude Code, Codex, Cursor and Gemini. | SKILL.md is the router; each step reads only its own reference. Frontmatter is standard-only. | [packaging-and-workflow.md](packaging-and-workflow.md) |
| Trackers differ, but every issue reduces to title, body, comments, attachments and acceptance criteria. | One intake contract, a reader per tracker, plain text as the fallback. | [packaging-and-workflow.md](packaging-and-workflow.md) |
| Pages are skimmed, not read: people scan headings and pictures, folded content often goes unopened, and a diagram beside a caption beats separated text. Markdown inside HTML doesn't render in Obsidian. | Pictures with one-line captions stay visible; detail sits in single-block HTML toggles (tested in Obsidian and on GitHub) whose titles state the conclusion; blockers are never folded. | [visual-pages.md](visual-pages.md) |
| AI review tools pick the diagram from the kind of change (sequence for API flows, ER for schema, class for hierarchies, flowchart for logic, none for trivial ones). Numbered diagram steps that match a numbered walkthrough help people link picture and code. | "How it works" picks its diagram type by that rule, and the code walkthrough uses the diagram's step numbers. | [visual-pages.md](visual-pages.md) |
| Learning links rot and guessed links mislead. YouTube's oEmbed endpoint and LinkedIn Learning's redirects can be checked without an API key. | One specific video (YouTube, or one video inside a LinkedIn Learning course) and one page to read per idea, the architecture or system design idea first, each checked live by `grasp-tools check-link` when the page is written and dated, with title and channel taken from the check. | [visual-pages.md](visual-pages.md) |
| An instruction file is advice: direct commands are followed more often than conditional ones, and compliance falls late in a long session. Hooks are the documented way to make something happen at a fixed point. | `setup` adds an 18-line block to `AGENTS.md` that opens with a direct command, and offers a Stop hook (`grasp-tools record-check --hook`) that reminds once when files changed and no record was written. | [run-records-and-overviews.md](run-records-and-overviews.md) |
| Agent summaries run long and sometimes claim changes that were never made; one shared log file conflicts on every merge; logs that hold command output leak credentials. | One run record per task, five fixed one-sentence lines, "Checked" quotes a result line or says "not checked", no raw output, and a table of all runs that is built by a command. | [run-records-and-overviews.md](run-records-and-overviews.md) |
| A newcomer asks first what the app can do and how those things connect; context and container views are enough architecture for most teams; diagrams stop helping past about 20 boxes; ungrounded repository summaries are often wrong. | The app map lists core features and draws how they connect, each core feature gets a short page, diagrams hold about 10 boxes, every row names its file and guesses go under "Not sure yet". | [run-records-and-overviews.md](run-records-and-overviews.md) |
| Systems made of several repositories are documented per project, with one landscape page derived from them. | `grasp-tools projects` finds sub-projects; each gets its own app map and a workspace map shows what passes between them. | [run-records-and-overviews.md](run-records-and-overviews.md) |
| Spec tools show planned against built as a delta, plan files tick as the agent works, and one CLI installs a skill into many agents. | A step list ticked during the build, a "Planned and built" table, a Concepts section with the long text folded, length limits the linter enforces, and a one-line install. | [prior-art-2026-11.md](prior-art-2026-11.md) |
| Reading a generated explanation does not build understanding; answering questions about the mechanism does, and self-judged understanding is unreliable. On a real project every explain-back sat unanswered because the path connected skills use never asks. | `walk` is a guided session the owner starts on a finished page: questions after real code lines, the gaps and the owner's own answers written to the page, a checked lesson for each gap. It never scores and never blocks. | [understanding-first.md](understanding-first.md) |
| A writer that retypes code or sees only the diff writes what it hoped happened. A page that no longer matches its files misleads, and maintenance is what kills tour tools. | Code reaches a page only through `grasp-tools snippet`, `coverage` proves every changed file is named, each page is pinned to its commits, and `sync` and `repair` find and rewrite stale pages. | [understanding-first.md](understanding-first.md) |

Open gaps: no study yet covers professionals learning from agent-built code over months, and
nothing ranks C4 against request traces against glossaries for learning. Treat the prediction
question as a cheap bet, not a proven one. No study measures how well an end-of-task rule or a
Stop-hook reminder holds up in practice; grasp's own live check is a handful of runs, not a
measurement.
